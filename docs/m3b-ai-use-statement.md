# Milestone 3 Stage 2 — Gemini / AI Use Statement

The following entries document the ChatGPT assistance used to reorganize the existing Compose project. The original visual designs remain the team's Figma designs; this work reorganizes and adapts the existing implementation rather than inventing new product screens.

| File | Prompt given (summary) | What AI produced | Team changes / checks required before submission |
|---|---|---|---|
| `SignInScreen.kt` | Separate the existing sign-in UI from the combined account screen into its own Compose screen file; preserve current validation, demo-account helper and password-help dialog. | A dedicated sign-in screen using the existing shared fields, buttons and branding components. | Compare labels, spacing and behavior with the Milestone 2 sign-in mockup; test valid and invalid credentials. |
| `CreateAccountScreen.kt` | Separate account registration into its own screen file and retain the existing form validation and sign-in switch. | A dedicated registration screen with name, university email, password and confirmation fields. | Compare the form with the registration mockup; test empty fields, invalid email, short password and password mismatch. |
| `HomeFeedScreen.kt` | Move the existing home-feed composable into a standalone file without changing search, category filters, condition/type filters or item selection. | A standalone home-feed screen and a Compose Preview using sample listings. | Compare the screen with the Figma home-feed design and test search, filters, empty results and opening an item. |
| `ItemDetailsScreen.kt` | Extract item details into a standalone screen, keep request eligibility and confirmation behavior, and make the request action injectable for navigation and preview. | A standalone details screen, callback-based request action and a Compose Preview with an Arduino sample. | Check all displayed item fields, own-item/unavailable/duplicate-request states and the request confirmation flow. |
| `CreateListingScreen.kt` | Expose the create-listing flow as its own screen while retaining the existing listing form and validation. | A dedicated create-listing screen that reuses the listing form component. | Compare fields and photo selection with the Figma mockup; test required fields and successful local publishing. |
| `MyActivityScreen.kt` | Extract the activity tabs into their own screen file and preserve listing, sent-request and received-request actions. | A standalone My Activity screen with existing edit, details, accept, reject and complete actions. | Test all three tabs and verify that each action updates the expected local state. |
| `NotificationsScreen.kt` | Extract notifications into their own screen file and preserve unread indicators, mark-as-read and relative timestamps. | A standalone notifications screen and its relative-time helper. | Verify notification filtering by current user, unread state and mark-all-as-read behavior. |
| `ProfileScreen.kt` | Extract profile into its own screen file while preserving profile editing, reuse totals and sign-out confirmation. | A standalone profile screen. | Check displayed user data, profile update, listing totals, completed-exchange totals and sign-out. |
| `EditListingScreen.kt` | Keep the existing edit-listing route working as a separate supporting screen while sharing the listing form. | A small edit-screen wrapper that passes the selected listing ID to the shared form. | Test that only the owner's available listing can be edited and that discard/save behavior remains correct. |
| `Routes.kt` | Centralize route names and route builders for all screens, including item and listing IDs and the activity tab. | Route constants and encoded route helper functions. | Verify every route name against the NavHost and test arguments containing spaces or special characters. |
| `AppNavGraph.kt` | Move the NavHost, bottom navigation, floating action button, auth transitions and screen destinations out of MainActivity into one navigation file. | A centralized Compose navigation graph connecting all screens. | Run every route from the UI, verify back behavior and ensure sign-in/sign-out return to the correct start screen. |
| `MainActivity.kt` | Keep the activity as the app entry point and delegate theme and app navigation to their dedicated files. | A small activity that calls the theme and `MaterialExchangeApp`. | Confirm the manifest still points to this activity and the app launches from a clean install. |
| `ui/components/Components.kt`, `AccountHeader.kt`, `ListingFormContent.kt`, `ui/theme/Theme.kt` | Move shared UI elements, account branding, the reusable listing form and theme tokens into clear component/theme folders. | Reusable Compose components and a separate Material theme definition. | Check shared styling on every screen and ensure the helper files are not counted as additional user-facing screens. |
| `domain/Domain.kt`, `data/LocalExchangeRepository.kt`, `viewmodel/ExchangeViewModel.kt` | Organize the existing domain, local repository and ViewModel files into their respective folders without changing the alpha's storage behavior. | Separate domain, data and ViewModel packages with imports updated. | Run unit tests and verify that local accounts, listings, requests and notifications still persist. |

## Team understanding and verification

ChatGPT was used to reorganize the existing Kotlin/Compose implementation into one file per Milestone 2 screen, extract shared components, and centralize route definitions and the NavHost. The team must compare each screen with the approved Figma mockups, run the app and tests, and review the route and state-handling code before committing. The alpha still uses the local repository described in the README; this refactor does not claim that Firebase has been connected. Every member should be able to explain the screen and route assigned to her in the distribution table.
